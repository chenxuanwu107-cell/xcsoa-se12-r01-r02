## Proposed distinction

An eligible Individual can use a computing/model provider as a **technical
processor for that Individual's permitted task** without giving an enterprise
customer a reusable Skill capability. This needs an express, narrow copyright
permission to the provider for the actual processing; the provider's corporate
status cannot be wished away. It is distinct from the forbidden arrangement in
which the freelancer merely operates the customer's Skill service by proxy.

The [English candidate, Section 4](LICENSE-CANDIDATE.en.md#4-no-organizational-operational-license-no-circumvention)
proposes that distinction, subject to legal and rights-holder approval. It would
cover necessary transmission, temporary copying, inference, task storage,
security/abuse handling, lawful retention, and necessary sub-processors only to
the documented extent accepted for a particular product. It would grant no
standalone Skill exploitation, resale, customer API, organizational deployment,
public GPT/plugin listing, unrelated model training or general product
improvement permission. An account's personal label alone proves none of this.

An incompatible mandatory provider grant requires a separately approved
rights-holder permission, a different contract/product, or a different execution
route. The custom license cannot amend a provider's agreement, bind an
unassenting provider, or authorize the Individual to promise rights not held.

The Services Agreement preamble uses an organizational Customer formulation.
Do not infer that every natural-person developer can accept that exact agreement
in the required personal capacity; contracting eligibility must be verified.
An API organization/workspace identifier alone does not decide the user's legal
capacity under this custom license. Product/country access eligibility and
regional agreements were not checked here; no account-access workaround is
proposed.

## Concrete cases

| Arrangement | Candidate assessment, if validly adopted |
|---|---|
| Individual runs a task on a personally controlled account, compatible necessary-processing terms confirmed, customer receives ordinary outputs | Potentially permitted by the proposed narrow processing clause. This is conditional, not a current grant or product-wide approval. |
| Individual uses a consumer account with training disabled | Still verify remaining service rights, retention, actual control and applicable regional terms; not automatically cleared. |
| Individual uses an API account legally held personally, without client access | Evaluate actual services agreement, endpoint/state handling, sub-processors and opt-ins. API access itself is not forbidden merely because it is an API; **enterprise customer calls to the Skill** remain forbidden. |
| Client owns/administers the workspace, key, automation or Skill integration | Not covered by independent professional use or this processor proposal. |
| Client calls the freelancer's Skill API or controls an unattended queue | Forbidden organizational/proxy capability, even if the freelancer owns the model account. |
| Shared GPT, team Skill library, marketplace plugin or hosted Skill service | Outside this narrow execution proposal; assess distribution/platform grants separately, with no automatic approval. |
| Other provider or incompatible mandatory training/improvement rights | No inferred exemption. Review its exact terms or obtain separate rights-holder permission. |

## Evidence needed to clear a particular route

Record product/feature, legal customer and actual operator, account control,
contract URL/version/region, required copyright acts and recipients, settings
and optional grants, retention/deletion exceptions, third-party data transfers,
and whether the Skill is shared. Map each required right to actual licensor
authority and the adopted clause or a separate signed permission. Keep sensitive
account evidence private and collect only what is necessary. A factual usage
summary is not a substitute for the actual agreement.

No general processor carve-out is deemed already valid. Adoption and legal fit
remain pending; the enterprise customer's restriction and ordinary-output
exception remain unchanged.
